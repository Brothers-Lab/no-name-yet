# Label Guideline


## 1. Purpose of Labels
- Keep our board and issues easy to filter  
- Help us quickly understand the nature of the item  
- Make discussions and issues consistent  
- Avoid creating too many unnecessary categories  
- Use the same label system across Discussions, Issues, and PRs  

---

## 2. Label Categories                    

### A. Type (What is this?)
Used to identify the nature of the item.

- **discussion** — brainstorming, questions, early thinking  
- **idea** — a thoughtful proposal that may become real work  
- **task** — a work item someone will execute  
- **question** — clarification needed  
- **bug** — something broken or incorrect  
- **improvement** — refactor or minor upgrade  
- **admin** — non-product work (ops, logistics, misc)  

---

### B. Context (Optional)
Purpose: What area of the project does this relate to?

You can choose **one or two** to give extra meaning.

- **product** — vision, direction, features  
- **tech** — technical design, architecture, coding  
- **workflow** — team process, rules, planning system  
- **doc** — documentation  
- **ops** — setup, CI/CD, automation  
- **feedback** — internal or external feedback  

---

## 3. Examples

### Example 1 — Discussion
“What is our product vision?”
- Type: `discussion`
- Priority: `P2` (optional)
- Context: `product`, `doc`

### Example 2 — Bug
“Login button not working”
- Type: `bug`
- Context: `tech`

### Example 3 — Task
“Write the label guide document”
- Type: `task`
- Context: `doc`, `workflow`

### Example 4 — Task
“Build the MVP”
- Type: `task`
- Context: `tech`

### Example 5 — Task
“Merge Rules Guideline”
- Type: `task`
- Context: `doc`, `workflow`
